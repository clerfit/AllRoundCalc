# Phase 12 — Complete Category Taxonomy and Calculator Inventory

**Purpose:** Establish one auditable catalogue for all 50 major AllRoundCalc subject categories, identify the calculator tools belonging to each category, distinguish existing tools from planned work, and prevent a category from being called complete while its required calculators or tests are missing.

**Phase 12 status:** Inventory and taxonomy definition in progress. This document is a scope baseline, not a claim that all 50 categories or every listed calculator are already implemented.

## Counting and completion rules

- Current active implementation baseline at the start of Phase 12: **248 calculator definitions in 9 registries** (Phase 11 inventory).
- An existing calculator is counted only when it has a unique registry ID and working calculation logic; a roadmap entry, mockup, disabled preview, or documentation row is not an implemented calculator.
- Each new calculator requires formula/algorithm documentation, variable and unit definitions, domain validation, worked reference examples, tests for valid and invalid inputs, contextual help for advanced inputs, and UI/accessibility coverage.
- Keep calculation local in the browser unless a feature genuinely needs public reference data. Never send users' entered values to analytics or a server by default.
- For medical, financial, engineering, or jurisdiction-dependent tools, clearly state limitations and obtain appropriate independent review before release.
- Category completion is measured as implemented unique tools / planned tools for that category. Do not mark a category complete merely because its landing page exists.

## Phase 12 delivery sequence

1. **Inventory and taxonomy:** retain this 50-category baseline; compare every category against the actual registry and mark each planned tool as implemented, partial, blocked, or not started.
2. **Canonical IDs and de-duplication:** assign stable IDs, aliases, units, and one owner category to each tool. Cross-listed tools should link to one implementation.
3. **Formula contracts:** create a formula catalogue for each new category before implementing calculation logic; include sources, assumptions, valid domains, units, worked examples, precision and known limitations.
4. **Category registries and engines:** implement in small reviewable batches, prioritizing high-utility foundational tools and shared conversion primitives.
5. **Interface and help:** make each calculator discoverable through search/category navigation; provide input validation, unit selectors where relevant, formula and limitation notes, and compact tooltips for advanced fields.
6. **Tests and accessibility:** add reference and invalid-domain tests for each tool, then browser interaction checks across desktop, tablet, and mobile. Automated accessibility checks do not replace human keyboard and screen-reader review.
7. **Audit and release:** reconcile unique IDs against the inventory, report implemented/partial/missing counts by category, run the complete test suite on the exact release commit, and retain an explicit list of independent domain-review blockers.

## Phase 12 acceptance criteria

- [ ] All 50 major categories are represented in the site's discoverable category catalogue.
- [ ] Every planned tool has a stable inventory ID and a recorded implementation status.
- [ ] Every implemented tool has a formula/algorithm contract, input ranges, units, assumptions, and limitations.
- [ ] Every implemented tool has valid reference examples and invalid-input/edge-case tests.
- [ ] No duplicate IDs or duplicate implementations are counted as distinct tools.
- [ ] Search and navigation expose all categories and all implemented tools accurately.
- [ ] Advanced calculators provide compact contextual tooltips.
- [ ] Unit choice is available within the relevant calculator; no global unit toggle is introduced.
- [ ] Source tests and Chromium desktop/tablet/mobile tests pass on the same commit.
- [ ] Remaining scientific, clinical, financial, engineering, legal, and human accessibility reviews are explicitly tracked rather than silently marked complete.
